Your (first) final year project

  • For most students the FYP is the first large solo project, and the final one in college
  • Nobody has managed one before, so nobody knows the traps
  • What can we learn from past students?
Ask: who has built anything bigger than a lab before? Usually very few hands.

Common disasters

  1. Work is lost or destroyed
  2. Biting off more than you can chew
  3. The code stops compiling or running after changes
  4. The report is neglected
  5. Unknown unknowns
Every one of these has happened to a past student. The next five topics take them one at a time.

You think you're the first?

Every disaster on the last slide has happened before. Learn from it.

1. Work lost: source control and backup

  • Push your work to GitHub 🔗4, GitLab 🔗5 or Azure DevOps 🔗6 every day
  • Get the free GitHub Student Developer Pack 🔗7
  • Back up the report too, not just the code

3-2-1 backup

3 copies, 2 kinds of storage, 1 off site 🔗8

A laptop stolen in week 10 should cost you an afternoon, not the project.

2. Too big: cut the scope

  • Build a minimum viable product first 🔗9
  • Sort features with MoSCoW: must, should, could, won't 🔗10
  • Only start a "should" when every "must" works

Hofstadter's law

It always takes longer than you expect, even when you allow for this law 🔗11

Ask each student to name their one "must" feature out loud.

3. It stopped working: keep it running

  • Change one thing at a time, then run it
  • Keep the last version that worked, and demo from that
  • Write the setup steps in a README 🔗14
  • Try it on another machine before demo day
If the demo breaks on the day, you go back to the version that worked and carry on.
It works on my machine🤷
💻📦Then we'll ship your machine

Or use a dev container, so it works on every machine 🔗15

Try your project on a lab machine or a friend's laptop before demo day.

Know what you depend on

  • Pin your package versions
  • List every library in the report
  • Don't update anything the week before the demo
  • xkcd 2347, Randall Munroe 🔗16, CC BY-NC 2.5 🔗17
An update the week before the demo is how working code stops working.

4. The report: write it every week

  • Keep a project log, in Markdown 🔗18
  • Save every source to Zotero the day you read it 🔗19
  • Take screenshots as you build. They are your evidence

Rule of thumb

Every week: one log entry, some report text, one meeting note

The report is marked too. A great app with a rushed report loses marks.

5. Unknown unknowns

  • Things you don't know that you don't know 🔗21
  • Try the riskiest part first, in weeks 1 and 2
  • Keep a short risk list and update it weekly
  • Show your supervisor something running every week

Early surprises are cheap

An API that doesn't do what you need costs a day in week 2, or the project in week 11.

Ask: what is the one part of your project you have never done before? Do that first.

AI tools

  • Check your college's AI policy and declare what you used
  • Note in your log what the AI wrote
  • You must be able to explain every line
Copilot wrote it🤖
😰"Explain line 42"
The demo and Q&A will find any code you don't understand.

The presentation and demo

  • Slides: PowerPoint, or HTML with reveal.js like this deck 🔗1
  • Record a backup video of the demo, for example with OBS Studio 🔗23
  • Demo from the last version that worked, not your latest change
  • Rehearse with a timer, twice
Wi-Fi fails, laptops update, servers sleep. The video means you still get to show it.

Help and support

  • Your peers. Swap demos and review each other's README
  • Your supervisor. Bring questions, not just updates
  • Explain the bug to a rubber duck first 🔗24 🦆
  • Search Stack Overflow, and ask with a small example that shows the problem 🔗25
Being stuck for a week is a choice. Ask after an hour.
